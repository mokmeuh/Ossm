# OSSM Control Design Contract

## Scope

This contract covers the Android Compose control surface and its embedded remote-control web surface. Preserve the Android dark graphite instrument-panel language and the remote web surface's dark/glass treatment; avoid a broad redesign of Scan, Profiles, Diagnostics, Funscript, or Video Sync.

## Tokens

- Background: solid `OssmBackground` (`#0C1219`) for Android screen roots; `OssmSecondary` aliases the raised surface (`#202C38`). Android screen roots do not apply a background gradient.
- Cards: `GlassCard` uses the solid `OssmGlass`/`OssmSurface` surface (`#16212B`) composited at low tint over the surface, with the uniform `OssmGlassBorder` (`#364858`); selected/control containers use `OssmSurfaceRaised`.
- Primary controls: `OssmPrimary` and `OssmPrimaryLight`.
- Accent controls: `OssmAccent`.
- Warning/state controls: `OssmWarning`, `OssmConnected`, and `OssmError`.
- Text: `OssmOnSurface` (`#EFF4F8`) for primary copy and `OssmOnSurfaceMuted` (`#AFBDC9`) for supporting copy; shared typography supplies readable headings/body/labels, with compact labels remaining at least 11sp where the control contract requires it.

## Control Primitives

- The Internet session card (Profiles/Reglages) shows the session state, the private link with explicit Copy and Share buttons (the link is never copied automatically), and Start/Stop and Regenerate actions. While a remote session is active, the Control screen shows a compact banner with the local maximums and the live values sent by the site, and warns when the speed maximum is 0%.
- The remote web surface mirrors the existing dark glass palette, uses a responsive single-column control card, native range inputs with visible values, and a persistent STOP action. It never invents firmware commands: every action routes through `ControlSessionStore`.
- The private token lives in the URL fragment so it is not sent in the initial HTTP request or retained in server request logs. JavaScript exchanges it only through an Authorization Bearer header. The server expires after 60 minutes; loss of authenticated browser heartbeats stops motion locally.

- STOP remains the dominant protected action in every mode, including Live, and must never be covered by the pattern bubble or radial gesture. Live keeps no Pause action; release is its normal slow-return path while STOP remains an immediate cancellation.
- 2.3.28 compact STOP bar (portrait, `ui/components/StopBar.kt`): a wide red rounded bar (`OssmStop` with `OssmError` border, 14dp corners, bold white "STOP" 22sp, contrast ~6:1) that takes the row width minus the pause button, 56dp high (target >= 48dp), TalkBack label "STOP, arrêt immédiat" and first in traversal. Pause/play sits on the same line at 56dp. The round `StopButton` is unchanged for other screens and for the landscape side rail.
- The connection/machine status banner (OSSM non connecté, USB, calibration, error) is never inserted in the STOP line: it is a compact one-line banner (ellipsis) under the bar in portrait, and the existing boxed banner at the top of the content in landscape.
- Pause/play keeps a circular footprint outside Live (56dp in the portrait STOP line). Settings uses the existing surface/border tokens in a 48dp square target inside the active control-card header.
- The control-card header renders only the active mode name. Its opener, weighted title, settings, and optional Save action occupy one non-overlapping row; Save remains absent in Live.
- Sensation is one scalar slider from 0% to 100%, with neutral labeling and matching +/- controls.
- Live mode uses the dedicated anchored real-time surface (see "Live Anchor Position Surface"). The finger distance from its anchor, counted only above the anchor line, is the desired target while contact is active; normal release starts the phone-owned slow return, while cancellation/STOP sends the explicit immediate stop path and never commits a final target. UI callbacks expose desired positions only; transport cadence and actuator slew remain outside the UI layer.
- The settings gear exposes Precision for the active pattern. Overrides are keyed independently by pattern and default off until explicitly enabled, including outside Live; changing one pattern never changes Simple Stroke, Live, or another mode. In Live only, the same dialog also exposes the existing invert-direction switch; the Live card never renders a standalone invert row.
- The settings gear opens a responsive rectangular `ControlSettingsDialog`, not a narrow alert. It follows the phone width with 16dp outer gutters, caps its width on larger windows, keeps its title and close action fixed, and gives the settings body sole ownership of vertical scrolling. The surface uses `OssmGlass`, `OssmGlassBorder`, and the existing dark-glass elevation language.
- The Profiles update card includes a local OTA section with two independent actions: `Prêt à recevoir` advertises a short-lived authenticated receiver on the local network, and `Partager ma version` discovers any OSSM receiver and uploads the installed APK. Either phone may perform either role; Quick Share is not part of the primary flow. After a complete package/version/signature check, the receiver opens Android's installer and leaves the final confirmation to the user.
- Local OTA 2.3.32: the receiving phone shows a large black-on-white pairing QR (≥ 85 % of the card width, max 360dp) with the addresses as text below. The sender has `Scanner le QR`, `Envoyer à une adresse` (address only) and `Partager ma version`. Both phones then show the same 2-digit number in 56sp bold: the receiver asks « Le nombre NN est-il bien celui affiché sur l’autre téléphone ? » [Oui] [Non], the sender shows the number + « En attente de confirmation » with Annuler. Buttons ≥ 48dp, numbers announced to TalkBack, status messages are polite live regions.
- Live settings expose a persisted integer acceleration percentage from 10% to 100%, defaulting to 33%. The value is absent outside Live. Changing it commits the displayed integer without changing Precision, inversion, the Live position range, homing, mapping, or release-to-stop behavior.
- `PressHoldInfo` is the dedicated explanation affordance beside setting labels. Pressing only its 48dp icon target reveals a non-modal dark-surface explanation overlay; release, pointer cancellation, or movement beyond touch slop hides it. The affordance never wraps a row or slider, and the overlay has no pointer handler, so slider gestures remain independent.
- Pattern selection uses a fixed small opener on the left side of the control title. Opening it replaces the visible control surface with one picker overlay; the picker uses a vertical list and closes after selection or dismissal. The opener is not draggable.
- Safety settings expose persisted depth-limit sliders and explicit microphone targets for speed, depth, and sensation within the existing dialog.
- Random-capable control modes expose a compact four-button preset rail below Speed and Depth. Each button shows the minimum at left, maximum at right, and an optional saved speed in a smaller centered line. A single tap saves the displayed control values, a double tap applies the preset through the existing guarded commit path, and a long press opens the dark-glass range editor with minimum, maximum, and the optional “save current speed” checkbox.

## Compact Active Layout

- The active control surface never owns vertical scrolling. Pattern pickers and dialogs may scroll internally, but the STOP rail and active control card remain fixed in the available window.
- Portrait uses a compact 56dp top action line (2.3.28): the STOP bar takes the width and pause/play (56dp) sits beside it outside Live. Live keeps the STOP bar visible while omitting Pause so the radial gesture cannot cover its cancellation path.
- Landscape uses a narrow 112dp side action rail with STOP and pause/play outside Live; Live keeps the same rail with STOP only. STOP stays fully visible, above all overlays, and is never covered by the pattern picker.
- The Moto G acceptance bounds are the real app content area after system bars and bottom navigation. The Live card takes the flexible remaining height while retaining comfortable outer margins and leaving the header, settings gear, and bottom navigation visible. All active Live information, including readiness feedback, value, fine range, and endpoint labels, must fit without a main-surface swipe in both orientations.
- Compact cards use the existing `OssmBackground`/`OssmSecondary`, `GlassCard`, border, and accent tokens. The redesign does not introduce a second material language or generic component system.

## Precision Scalar Slider

- `PrecisionScalarSlider` is the reusable gesture and state primitive for scalar setting controls only. Its effective horizontal interaction region is at least 56dp high while its visual track remains 6dp and its thumb remains visually compact.
- Pointer down anywhere in the enlarged region preserves the current value. Horizontal movement is relative to the pointer-down value; a tap or vertical-only movement never maps to an absolute track position.
- Movement up to 8dp from the last stationary anchor is treated as normal finger jitter. Movement beyond 8dp updates the value and restarts the current level's 1500ms stationary clock.
- Global state maps the full track to `0..100`. Each completed 1500ms stationary interval activates exactly one centered level around the finger's current mapped value: `+/-30`, then `+/-20`, then `+/-10`, then `+/-5` percentage points.
- In a precision level, horizontal displacement is relative to the value captured when that level begins and is scaled across that level's displayed range. Meaningful movement retains the reached level/range while dragging, makes the new mapped value the center candidate for the next level, and restarts the 1500ms timer.
- Near 0 or 100, a centered window shifts inside the global bounds to preserve as much of its intended span as possible. Visible feedback names the active level and exact integer range; French and English resources carry equivalent status and accessibility wording.
- Entering each precision level emits one `TextHandleMove` haptic. Recomposition or stationary timer ticks do not repeat haptics.
- Successful pointer release commits exactly once and immediately returns visual feedback to `0..100`. Pointer cancellation, disabled-state transition, or disposal cancels without commit or ghost callback. A fresh gesture after orientation change starts from the latest external value.
- Existing +/- controls remain available and preserve their guarded incremental/ramp behavior; their effective target is at least 56dp.

## Live Anchor Position Surface

- Live uses a dedicated anchored control surface with a minimum `420dp x 280dp` portrait footprint and `180dp x 280dp` compact-landscape footprint, then expands to consume the remaining card height. The full surface is interactive, not only a narrow rail.
- 2.3.24 upper half-disc contract (supersedes the 2.3.19 full-radial mapping): there is no fixed center. The whole Live surface is the touch zone; the first pointer-down, anywhere, becomes the ANCHOR and takes the current logical position `B` (`B = 0` when the carriage rests at home). Only the half-plane ABOVE the anchor's horizontal line adds depth. With the finger strictly above that line (`fingerY < anchorY`), the value follows the RADIAL anchor-finger distance `d` (sideways movement counts too), normalised by `R_top`, the distance from the anchor to the farthest TOP corner of the surface, measured once at pointer-down: target = `B + clamp(d / R_top, 0, 1) x (100 - B)`; that corner is 100 and anything beyond clamps to 100. On or below the anchor line (`fingerY >= anchorY`) the target stays exactly `B`: it never rebounds positive and never goes below `B`. When the anchor lands at the very top (`R_top` ~ 0), `R_top` is floored at `LIVE_ANCHOR_MIN_REACH_DP` (48 dp). The result stays a logical Live percentage: phone range, inversion and the device-proven inverse mapping apply unchanged downstream.
- Pointer-down never emits a jump: the anchor equals the current position. A new touch during the slow return therefore anchors at the current returning position (`B > 0`), stops the return there, and moving away only adds depth beyond it; coming back to the anchor gives `B`, not less. Releasing restarts the normal slow return from wherever the gesture ended.
- During an engaged native gesture there is no touch-target slew (the former 80 %/s cap): every distinct integer target goes straight to the same coalesced BLE scheduler, bounded only by the user speed maximum/acceleration envelope and the firmware limits, so fast anchor <-> far round trips follow the finger. The phone-owned 80 %/s `LiveTargetSlew` remains only as an entry ramp when a gesture's first sample is more than `LIVE_DIRECT_ENTRY_TOLERANCE_PERCENT` (5 points) from the current position (e.g. TalkBack `setProgress`, stale snapshot); it hands over to direct follow once the target is within that tolerance. Browser (remote) targets keep the 80 %/s slew. Live entry still uses `convergeLiveEntryToHome` before `streamingReady`.
- A stale Store/BLE snapshot never overwrites an active anchored gesture. Above the anchor line horizontal and vertical movement both contribute through radial distance; below it neither does; duplicate transport positions remain filtered by the existing BLE scheduler.
- Normal finger release and remote `EndLiveTouch` start a phone-owned return to logical `0` at a named maximum of 20 percentage points of stroke per second, so 100% takes at least five seconds. The return is target-slewed and does not use an immediate STOP.
- Explicit STOP, BLE/session loss, cancellation/disposal, disabled-state transition, orientation change, and leaving Live cancel the return and all queued Live targets immediately; they never start a return. STOP remains visible outside the radial surface for this purpose.
- Live entry keeps the existing sequential navigation, mandatory homing, setup, inverse mapping, 2..98 keepout, and `streamingReady` gate. 2.3.17 entry convergence: the firmware enters streaming without moving, and a single Live target is executed in at most ~250 ms (deadline rebased to receipt + 250 ms), so the first touch used to drag the carriage across the stroke to Home almost instantly. After the band is verified and BEFORE `streamingReady` opens, the phone reads the native `positionMm`: within `LIVE_ENTRY_HOME_TOLERANCE_MM` (6 mm) nothing moves; otherwise it caps `set:speed` at `LIVE_ENTRY_HOMING_SPEED_PERCENT` (3 % of the 1000 mm/s firmware maximum, ~30 mm/s), sends one Home target whose duration is proportional to the distance (honoured by the text transport), waits for it, then writes `set:speed:0`. Touch targets stay refused meanwhile; STOP/cancellation or link loss aborts the convergence and leaves Live disarmed. Unknown position (older firmware) keeps the historical behaviour; with the user inversion the unknown distance assumes a 250 mm stroke.
- The surface draws no fixed center. While a finger is down it draws the anchor marker where the finger landed, the anchor's full-width horizontal line, the lower half greyed with the label "reste à B" (`reste à 0` at rest), upper reach half-circles centered on the anchor at 25/50/75 % of `R_top` and a dashed 100 % half-circle through the farthest top corner, each labelled with its mapped value (25/50/75/100 when `B = 0`), and the finger indicator (accent above the line, muted below) with the anchor-to-finger line only while above. The integer percentage and the legend "Touchez : ce point = 0 · montez = plus profond" stay in the header. TalkBack is unchanged: it exposes the value, `setProgress`, and Increase/Decrease custom actions (±10 points); each accessibility step sends one target and then follows the normal slow return to 0, never a held position without a finger.
- Code names: `LiveAnchorPad` (composable), `LiveAnchorState` / `liveAnchorReach` / `liveAnchorFraction` / `liveAnchorTargetPercent` (pure geometry, `ui/components/LiveAnchorState.kt`). They replace the former `LiveRadial*` names.
- Live recording/replay, phone limits/maxima, acceleration, and the device-proven inverse mapping remain outside the radial geometry and continue to use their existing transport seams.

## Real-Time Slider Responsiveness (2.3.17)

- Control drafts (speed, depth range, sensation) are owned by the finger while it moves. External `uiState`/remote values reach the drafts only after a 250 ms quiet period following the last local edit and always from the latest state; starting or ending a remote session applies immediately. The depth `RangeSlider` commits the last range the finger produced, and its tap detector is not restarted on every value change.
- Non-urgent real-time parameter writes are latest-wins per parameter and written one acknowledged GATT write at a time; a direct (committed) write supersedes a pending value and any `set:speed:0` drops all pending values, so no stale slider value can be written after STOP. The diagnostics journal keeps the newest 500 lines.

## Accessibility Constraints

- Slider semantics expose the current value, active precision level/range, enabled state, and a progress action. The semantics bounds cover the full 56dp interaction region, not only the visual track.
- Toggle and checkbox rows expose a minimum 56dp effective height and one coherent label/state target; descriptive copy must not create a second ambiguous click target.
- `PressHoldInfo` exposes an explicit localized content description and remains separate from switches and sliders. Setting meaning is never encoded only by the transient overlay: the setting label, current value, and control semantics remain available to TalkBack.
- Compact layouts must preserve readable 11sp minimum labels, single-line pattern names with ellipsis, sufficient contrast from existing tokens, and logical TalkBack traversal with STOP before the active control card.
- Precision feedback is not color-only. Text and one haptic per entered level communicate the state; cancellation and release reset are announced through the returned global-range description.

## Accepted Debt

- Deterministic state and layout-contract tests cover this task. Per the user-owned QA boundary, rendered Moto G portrait/landscape appearance, physical thumb reach, system-bar insets, font scaling above 1.0, and TalkBack traversal remain device-level acceptance.
- Range sliders in safety dialogs keep their existing Material gesture behavior in this slice. The progressive primitive applies to scalar sliders; dual-thumb range editing requires a separate ambiguity and safety design before migration.

## Accessibility And Safety

- Pattern names stay on one line with ellipsis; the full label remains available to accessibility services.
- Connection status is not shown in the Control header. Safety, calibration, and error messages remain visible.
- Swipe navigation between app sections is disabled in the main pager; bottom navigation remains the explicit route control.

## Voix Mode (2.3.26, base)

- Pattern key `voice`, label "Voix", listed after Live. It reuses the STREAMING entry unchanged (verified band, `convergeLiveEntryToHome`, `streamingReady` gate) and has its own scrollable panel instead of the Live pad; no record button, no pause/save actions. The browser cannot select it.
- Base only: no speech recognizer, no grammar and no network. The screen shows "IA vocale sur l'appareil : non installée", the planned sequence (e.g. `Fond 100 % en 2,5 s → maintien 2 s → Retour 0 % en 0,6 s`, current step in bold), the last decision (compris / refusé hors bornes / non compris / STOP / Live pas prêt), a "Vitesse max (voix)" slider and a full-width STOP button. The global STOP stays visible as for Live.
- A plan is a list of `VoiceStep {target 0..100 %, moveMs 200..10000, holdMs 0..10000}`, at most 12 steps, validated strictly (one bad step rejects all; nothing is clamped). The voice speed maximum (400 %/s at 100 %, intersected with the remote envelope maximum) lengthens any move that would be faster. Logical targets are scaled into the hard depth limits, then follow the ordinary Live path (inversion, remote envelope, BLE ceiling).
- Execution is linear per move with 40 ms targets; a new plan replaces the current one when the current move ends (immediately if flagged immediate, or during a hold/idle). The end of a plan stays in place. STOP (button or `voiceStopNow()`), pause, mode exit, Live touch/remote target, BLE/streaming loss and session end cancel it. Nothing moves at mode entry until a plan is accepted.
- Seams for the future on-device model: `VoiceCommandInterpreter` (audio or text -> steps / STOP / not understood; `NotInstalledVoiceCommandInterpreter` by default, `FakeVoiceCommandInterpreter` for tests) and `VoiceAudioSource` (`AudioRecord` 16 kHz mono PCM16, memory only, never stored; not wired to the UI yet). The diagnostics journal only records decisions (plan accepted/rejected, STOP), never audio or text.

## Voix IA sur l'appareil (2.3.27)

- Pipeline entirely on the phone (no network): microphone 16 kHz -> Silero VAD -> Parakeet TDT v3 (sherpa-onnx, offline decode per speech segment) -> STOP keyword on the text (stop/stoppe/arrête/arrêter/pause, accents and punctuation ignored, any occurrence wins) -> Gemma 3 1B int4 via LiteRT-LM (GPU, CPU fallback) -> JSON steps -> the existing strict validation and runner.
- The STOP keyword calls `voiceStopNow()` as soon as the segment is transcribed, without waiting for the LLM; a new segment cancels the interpretation in progress.
- LLM: short French instruction + 9 few-shot turns, near-greedy sampling (top-k 1, temperature 0.1), one fresh conversation per phrase (prepared in advance). Output `[{"cible","duree","maintien"}]`; Markdown fences tolerated, everything else strict (integers, known keys). Invalid JSON or `{"erreur":…}` = "Non compris", nothing moves; out-of-bounds = "refusée (hors bornes)".
- Panel: AI state (idle / "Chargement de l'IA vocale…" / prête (GPU|CPU) / modèle manquant with expected paths / modèle illisible / erreur), Écouter / Pause micro button (RECORD_AUDIO requested on first use, enabled only when ready), last transcript, measured latencies (end of speech -> text, text -> steps), planned sequence. Nothing moves while loading. No audio is stored; transcripts are shown only, never journaled.

## Voix (2.3.28)

- Header: the long explanation text is replaced by a round italic "i" button (48dp, same surface/border as the gear) placed before the gear; TalkBack "Informations sur le mode Voix". A tap opens a short dark-glass dialog (Fermer).
- No STOP inside the Voix panel any more: the global STOP bar at the top is the only STOP button; the spoken STOP keyword (before any LLM) and `voiceStopNow()` stay active.
- "Profondeur" two-handle range (the existing `DepthRangeEditor`, same style, +/- on the last touched handle), persisted in DataStore (`voice_depth_min/max`, default 0..1) and always intersected with `depthLimitMin..depthLimitMax` (5 % minimum span); the remote envelope still applies downstream (`sendStreamPositionTarget`). Voice targets 0..100 % map to [min, max] (0 % = minimum, 100 % = maximum).
- Range change while a plan or motif runs: the safest policy is a clean CANCEL (no STOP, no new target, the carriage holds), because durations were bounded for the old mapping. An idle runner is re-anchored on the current scalar; a new plan/motif whose start lies outside the range first joins the nearest edge through the existing bounded `LiveTargetSlew` (80 %/s), then starts: no jump. A residual gap larger than one legitimate tick is also routed through that ramp.
- Each accepted plan or motif arms the Live speed exactly like the first touch (`BleManager.armLiveSpeed`, same phone ceiling) before its first target; every refusal (not connected, streaming not ready, speed max 0, transport) is journaled under VOICE/LIVE, plus one line per step ("Voix : étape i/n cible X % en N ms"), never the spoken text.
- Continuous motif: `{"motif":"va-et-vient","profondeur_debut","profondeur_fin" 0..100,"vitesse_debut","vitesse_fin" 1..100,"montee_s" 1..300}`, strict (otherwise "Non compris"). Strokes between the range minimum and a peak rising linearly over `montee_s`, cadence = vitesse % of the Voix speed maximum (envelope included), then continuous until STOP or a new instruction; it starts from the current position. Modulations `{"modulation":"plus_vite|plus_lent|plus_profond|moins_profond|garder"}` start from the current levels (±15 speed points, ±10 depth points; "garder" freezes). The panel shows the motif line. Phrases containing a STOP word (e.g. "arrête d'augmenter") still STOP first, by design.

## Voix (2.3.29) — vitesse réelle et sécurité

- Speed-sized targets: the binary Live firmware executes each target within ~250 ms, so the 2.3.28 1 %-per-tick stream moved at ~4 %/s. Voix targets now use the `VOICE` producer (timeline: the requested duration is honoured, latest wins), each carrying its own duration (<= 200 ms) and a step of speed x duration (integer, <= 25 logical points), emitted at the start of its segment. Step-plan durations are respected; motif turning points are always emitted, so the peak is really reached and the cadence is the requested one.
- Scale: logical 0..100 covers the whole Voix range (default 0..1); 100 = fond, 0 = départ; the Live inverse mapping (100 - raw) is applied only in the BLE layer, as for touch. "Vitesse max (voix)" stays 50 % by default (400 %/s at 100 %, effectively capped at 125 %/s by the 25-point step).
- Motif start floors (never above the Voix range / speed maximum / envelope): profondeur_debut >= 30, profondeur_fin >= 60, vitesse_debut >= 20, vitesse_fin >= 40; the prompt asks for 30->90 %, 20->70 %, 25 s for "commence lentement".
- No automatic resume: app in background / onStop / screen off, missed connection ping (link suspect) or BLE loss cancel the Voix sequence/motif with STOP (speed 0). Background and link suspect also STOP Naturel, progressive, auto, Live replay/returns (background excepted while an Internet remote session owns the motion: it has its own heartbeat loss -> stop). Nothing moves on return without a new instruction.
- STOP layers: (1) wider keyword list including observed Parakeet mis-transcriptions ("right", "I right", "all right", "top", "step", "wait", "non", "fini", "ça suffit", "enough"...); a false positive only stops. (2) Parakeet TDT v3 has no language/prompt parameter in sherpa-onnx 1.13.8 (`OfflineTransducerModelConfig` = encoder/decoder/joiner only); French cannot be forced. Hotwords would need modified_beam_search + a BPE vocab (untested, not enabled). A `KeywordSpotter` exists in the AAR but needs a dedicated KWS model: documented option, not added. (3) "STOP rapide par mot court" (on by default, persisted `voice_short_word_stop`, shown in the panel): a VAD segment of 100..800 ms spoken while Voix moves is a STOP before ASR/LLM. (4) Volume up/down: immediate STOP while the Control page is shown and a motion mode is active (Voix, Naturel, Live, running pattern); the key event is consumed (volume unchanged), otherwise normal volume behaviour.
- Journal: "STOP vocal (bouton|mot-clé|mot court|touche volume)", one line per motif ("Voix : motif prof a→b %, vitesse c→d %, montée N s") and per level change (modulation, final level reached), one per step; never one per target.

## Voix (2.3.31) — règles avant Gemma, garde anti-hallucination
- Order: transcript -> STOP keyword (always wins) -> `VoiceTranscriptGuard` (empty, punctuation only, typical Whisper hallucinations such as "Sous-titres réalisés par…", "Merci d'avoir regardé", "Abonnez-vous", "Merci.", a word repeated more than 3 times in a row, > 200 characters, segment RMS < 0.004) -> `VoiceRuleParser` (deterministic French grammar) -> Gemma only when the rules are not certain (every word must be understood). Rules and Gemma produce the same objects, validated by the same strict validators.
- Panel lines: "Interprétation : règles|Gemma · N ms" under the latency line; "Transcription ignorée : <raison> (aucun mouvement)" in warning colour when the guard ignored a segment.
- Settings toggle rows (precision, guards, overlay, reasoning relay) are one toggleable target (`Role.Switch`, label + switch); the press-and-hold "i" stays outside and exposes its explanation to TalkBack (state description, double tap toggles it).

## Session Internet (2.3.31) — reconnexion
- A transient host WebSocket loss (network, OkHttp ping, broker close 4000 heartbeat_timeout/lease_lost, broker "capacity" while reconnecting) emits the STOP at once, keeps the remote envelope, and re-opens the same link with backoff 1, 2, 4, 8, then 15 s, at most 20 attempts. The card shows "Reconnexion… (essai n/20)" (warning colour), then "Reconnecté; attente d'une nouvelle commande du contrôleur": no motion is resumed, the browser must send a new command. Broker errors (forbidden/expired/invalid), close 1008 revoked/expired, local expiry and stop() end the session as before; 404/410 on reconnection recreates the session (new link), like renewal.
